# ADR-0012: 데모 시계 — 가상 시드를 재시드하지 않고 오늘로 민다

- 날짜: 2026-09-18
- 상태: 채택
- 관련: ADR-0004(가상 시드) · ADR-0006(쓰기 관문) · ADR-0009(공유 DB)

## 맥락

시드는 **만든 날을 오늘로 보고** "3일 전 신청 · 2주 전 완료"를 찍는다. 그 뒤로는 달력만 흐른다.

라이브(공유 DB)는 8월 19일에 한 번 시드를 복사한 뒤 그대로였다. 한 달 뒤(9월 18일) Aside 로
라이브를 점검하니:

- **조회 첫 화면이 모든 방문자에게 0건** — 기본 조건이 '내 담당 · 최근 15일'인데 가장 최근 요청이 한 달 전이다
- 보드의 진행 카드가 전부 D+16 ~ D+49 로 기한 초과
- '최근 완료(30일)' 컬럼·알림(30일 창)·월별 추이의 이번 달이 비어 가는 중

포트폴리오를 여는 사람이 가장 먼저 보는 화면이 "조건에 맞는 요청이 없습니다"였다. 코드는 멀쩡하고
배포도 green 이라 아무것도 경보를 울리지 않았다 — **날마다 조금씩, 조용히** 비어 간다.

로컬 파일 DB 도 같다. `SCHEMA_VERSION` 이 바뀔 때만 다시 만들어지므로, 스키마를 안 건드린 한 달 동안
로컬 화면도 똑같이 늙었다.

## 결정

**기준 시각(`NX_DEMO_CLOCK.ANCHOR`)을 두고, 하루 넘게 지나면 그 이전의 기록을 통째로 민다.**

- 시드가 기준을 적는다 = 시드를 만든 날의 끝(23:59:59).
- 읽기(`select()`) 전에 인스턴스마다 10분에 한 번 확인한다. 기준 이후 **만 하루**가 N 번 지났으면
  N 일 민다(`UPDATE ... datetime(col, '+N days')`). 기준도 N 일 옮긴다.
- 모두 UPDATE 라 쓰기 관문(`write()` — INSERT/UPDATE 만, 한 트랜잭션)을 그대로 지난다. 새 문을 열지 않았다.
- 쓰기가 잠긴 저장소(서버리스 메모리 DB)는 밀지 않는다 — 콜드스타트마다 오늘 날짜로 새로 시드되므로 필요도 없다.

### 지키는 불변식 (`src/lib/dev-seed/clock.ts`)

| # | 불변식 | 어떻게 |
|---|---|---|
| ① | **미래를 만들지 않는다** | 미는 폭 = 기준 이후 흐른 *만 하루* 수 → 옮긴 값 ≤ 기준 + N일 ≤ 지금. 그리고 값마다 `≤ 기준`을 다시 본다 — 옮길 요청을 고른 뒤 밀기 전에 끼어든 댓글·완료일('지금')은 제자리에 둔다(예상처리일은 계획이라 예외) |
| ② | **한 요청은 통째로 움직인다** | 요청·댓글·첨부 중 하나라도 기준 뒤에 생긴 게 있으면 그 요청은 이번에 안 옮긴다. 대상은 구문이 돌기 **전에** 고른다 |
| ③ | 이상치는 이상치로 | `1900-01-01`(이관분 날짜 누락)은 안 옮긴다. 먼 미래 값이 든 요청은 ②에 걸려 안 옮겨진다. 구시스템 이관분은 몇 년 전 기록이라 옮길 이유가 없다 |
| ④ | **두 번 밀지 않는다** | 모든 구문이 "기준이 아직 그 값일 때만"을 조건으로 달고, 기준을 옮기는 구문이 마지막이다. 서버리스 인스턴스 둘이 동시에 밀어도 뒤의 트랜잭션은 아무것도 안 바꾼다 |

방문자가 만든 티켓·댓글도 **다음 날부터는** 같이 밀린다. 세계 전체가 '만든 날 기준의 나이'를
유지한다 — 어제 단 댓글은 한 달 뒤에도 '어제'다. 데모에서는 이쪽이 맞다.

### 옛 공유 DB (표가 없던 DB)

- 새 표는 `npm run db:sync:remote` 가 만든다(빈 표). 컬럼을 `NX_SCHEMA` 에 붙이지 않은 이유가 이것 —
  공유 DB 는 컬럼 추가를 못 따라가지만 새 표는 따라간다.
- 빈 표면 앱이 **시드 공지에서 기준을 역산**해 한 번 적는다(가장 최근 시드 공지 = 시드일 − min(daysAgo)).
  ⚠️ 증인은 **보이는 시드 공지만**(`NTT_ID ≤ 시드 공지 수`)이다. 같은 `BOARD_DETAIL` 에 고객사 관리가
  **숨김 이력 행**(DELETE_FG='Y', REG_DT=지금)을 쓴다 — 처음엔 "공지는 앱이 안 쓰는 표"라고 잘못 전제했고,
  리뷰가 그 행을 증인으로 읽으면 기준이 오늘(미래)로 잡혀 **한 달 늙은 세계가 영영 못 따라잡는** 경로를
  재현했다. 역산 값이 지금보다 뒤면 '모름'(진단 500)으로 떨군다.
- `db:sync:remote` 는 공지 **문구만** 시드에 맞춘다(보이는 행만, 등록일은 그대로). 숨김 이력 행은 라이브가
  정본이고 번호가 로컬과 겹치므로 절대 건드리지 않는다.
- 표가 없으면 `/api/diag` 가 500 으로 신고한다. 화면은 멀쩡히 뜨는데 날마다 비어 가는 고장이라
  HTTP 상태로 드러내야 한다(P10 의 페르소나 드리프트와 같은 원칙).

## 결과 (트레이드오프)

- 얻는 것: 언제 열어도 "지금 운영 중인" 포털로 보인다. 라이브의 방문자 데이터를 버리지 않는다.
  코드 배포만으로 로컬·라이브가 함께 고쳐진다(공유 DB 는 sync 한 번).
- 포기하는 것:
  - **접수번호의 연월이 신청일과 어긋난다** — `HB-202608-003` 이 9월 신청일을 달고 있을 수 있다.
    번호는 식별자라 바꾸면 링크·이력이 깨진다. 번호의 연월은 "처음 만들어진 달"로 읽는다.
  - 본문에 적힌 달력 날짜는 못 민다 → 시드 문구에서 달력 날짜를 뺐다(공지 "8월 정기 점검 (8/20)" →
    "정기 점검 (이번 주 수요일)"). 새 말뭉치에도 절대 날짜를 쓰지 않는다.
  - 첫 요청이 하루 한 번 밀기를 기다린다(원격 DB 는 수백 ms).
  - **정기 업무의 '이번 달 생성'(LAST_RUN_YM)은 옮기지 않는다.** 실제 달력의 중복 생성을 막는 장치라,
    세계 시계를 따라 올리면 이번 달 회차가 조용히 사라진다(리뷰 재현). 그래서 달이 바뀌면 시드의
    '생성됨' 배지도 다시 '대기'가 된다 — 실제 운영과 같은 모습이다.

## 검토한 대안

- **주기적 전체 재시드(cron)** — 탈락: 방문자가 만든 티켓·댓글·첨부를 매번 버린다(ADR-0009 이 피한 것).
  재시드는 DELETE 가 필요해 쓰기 관문을 넓혀야 하고, 서버리스 함수 시간 안에 원격으로 수천 행을 다시
  넣어야 한다.
- **읽을 때 날짜를 보정(가상 '오늘')** — 탈락: 모든 날짜 조회·표시·D-day·필터에 보정이 스며든다.
  새로 쓴 행(진짜 지금)과 시드 행(가상 지금)이 한 화면에서 어긋난다.
- **기본 조회 조건에서 기간을 빼기** — 탈락: 첫 화면 하나만 가린다. 보드 D-day·최근 완료·알림·추이는
  그대로 늙는다. 그리고 '내 담당 · 최근 15일'은 사용자가 정한 작업 큐 설계다(957ee3a).
- **시드 날짜를 전부 상대값으로 저장** — 탈락: 원본과 같은 컬럼·형식(TEXT 벽시계)을 쓰는 이 저장소의
  전제(`src/lib/data/` 쿼리 구조 보존)가 무너진다.
