# ADR-0007: 원본 포털 메뉴 중 무엇을 이식하고 무엇을 버렸나

- 날짜: 2026-08-14
- 상태: 채택 (MVP 3화면 범위를 6화면으로 확장한다 — `non_goals` 의 admin 제외는 유지)

## 맥락

원본 포털 전체 38메뉴(서비스 관리 6 + 내부관리 27 + 상단 상시 5)를 훑은 분석 문서를 받았다. MVP 3화면(대시보드·조회·신청)은 끝났고, "이식할 가치가 있는 것"을 골라야 했다.

판정 기준은 셋이다.

1. **이 데이터로 진짜 돌아가는가** — 시드에 없는 도메인(계약시간 Pool, FAQ 인덱스, SP 정의)을
   새로 만들어야 하면 화면이 아니라 데이터 픽스처를 만드는 일이 된다.
2. **이미 만든 것과 겹치지 않는가** — 조회 화면이 이미 검색·상세·처리를 다 한다.
3. **재설계가 미완인 곳을 메우는가** — 이식이 기존 화면의 구멍을 닫아야 값어치가 있다.

## 결정 — 이식한 3종

| 이식 | 원본 | 왜 이것인가 |
|---|---|---|
| **업무 현황 보드** `/board` | `/taskboard` (STB01, JSP 105KB + JS 86KB) | 조회 화면과 **같은 데이터의 다른 시점**이다 — 조회는 "이 건이 어디까지 왔나", 보드는 "지금 무엇이 어디에 쌓였나". 카드 이동이 ADR-0006 의 액션 라우트를 그대로 소비해 쓰기 설계가 두 화면에서 검증된다 |
| **공지사항** `/notices` | `/notice` (상단 상시 메뉴) | `BOARD_DETAIL` 테이블과 시드가 **이미 있었는데** 열어볼 화면이 없어 대시보드 공지 위젯이 막다른 길이었다. "모든 위젯은 갈 곳이 있어야 한다"(UX 원칙)의 미완성 조각 |
| **알림센터** 상단 종 | `/api/notifications/*` 드롭다운 | 재설계 §3 이 "코멘트 4회 왕복 → 알림 1 + 클릭 1"을 전제로 담당자의 **취소 권유**를 설계했는데, 정작 신청자가 그걸 받을 통로가 목록의 작은 뱃지뿐이었다 |

### 이식하면서 바꾼 것

- **칸반 컬럼을 줄였다.** 원본은 상태 코드를 그대로 8컬럼으로 폈다. 우리는 실측을 반영해
  주 경로 4 + 완료 1 만 항상 그리고, 테스트 단계(5·6)는 카드가 있을 때만 나타낸다.
  7·8·10 은 도입 이래 0건이라 컬럼을 만들지 않는다.
- **완료 컬럼은 최근 30일만.** 완료가 전체의 95% 라 전부 그리면 컬럼 하나가 화면을 삼킨다
  (대시보드 도넛에서 이미 내린 판단). ⚠️ 자를 때 기준은 **완료일(SUCCDATE)** 이다 —
  목록 필터의 기간은 신청일 기준이라 "오래전에 신청돼 어제 끝난 건"이 통째로 빠진다.
- **드래그에 키보드 대안을 붙였다.** 원본은 드래그 전용이라 키보드로는 아무것도 못 옮긴다.
  카드마다 '다음 단계' 버튼을 함께 둔다.
- **알림을 새 테이블로 만들지 않았다.** 읽음선(`NX_OPTREPORT_READ_STATE`)에서 파생한다 —
  "내 건에 달린, 내가 아직 안 본 글"이 곧 알림이다. 알림 테이블을 따로 두면 실제 댓글과
  **반드시 어긋난다**(두 곳을 각각 갱신해야 하므로). 대신 두 가지를 더했다:
  - **요청 단위로 묶는다** — 낱개 글로 뿌리면 상태 로그 3건이 한 요청에서 세 줄로 뜬다
  - **최근 30일만** — 읽음선만으로 자르면 몇 달 전 종료건의 로그까지 알림이 된다.
    지난 일은 알림이 아니라 이력이다(목록 뱃지에는 그대로 남는다)

## 결정 — 이식하지 않은 것과 근거

| 제외 | 근거 |
|---|---|
| 이력 통합검색(STB04) | 조회 화면의 검색과 목적이 겹친다. 원본은 전용 인덱스 테이블(`NX_TKSEARCH_IX`)을 따로 두는데, 우리 규모(2,250건)에서는 `LIKE` 로 충분하다 |
| FAQ(FAQ01/02) | 테이블 7개(`NX_FAQ_*`)와 시드 말뭉치를 새로 창작해야 한다. 화면이 아니라 데이터를 만드는 일이 된다 |
| 운영보고서(조회/관리) | 계약시간(`NX_ECO_REMAIN_TIME`) 도메인이 통째로 없다. 신청 화면의 계약시간 스트립이 아직 `null` 인 것과 같은 이유 — 이식하려면 계약 모델부터 만들어야 한다 |
| SP 정합성 점검(STB02) | 서버에서 `svn.exe` 를 직접 실행한다. 이 프로젝트의 성격(단일 Next.js 앱)과 맞지 않는다 |
| 대량메일·푸시알림 | 외부 발송(SMTP/FCM)이 본체다. 데모에서 흉내만 내면 "되는 척"이 된다 |
| admin/* 27종 | `non_goals` 유지. 원본 분석 문서도 "제네릭 CRUD 1개로 압축 가능"이라 적었다 — 압축해도 얻는 게 CRUD 폼이라 포트폴리오 가치가 낮다 |
| 사용자 조회 · 메일 참조자 설정 | 조회는 신청 화면의 신청자 Combobox 가 이미 대체하고, 참조자는 신청 폼의 토큰 입력으로 흡수했다 |

## 결과

- 화면 3 → **6**(대시보드·조회·신청·보드·공지·공지상세) + 상단 알림.
- 새 의존성 **0개**. 드래그는 HTML5 네이티브, 팝오버는 이미 쓰던 Radix.
- 새 **도메인** 테이블 0개 — 공지 본문 컬럼(`NTT_CN`) 하나만 늘었다.
  (스키마 버전을 담는 메타 테이블 `NX_SCHEMA` 는 데이터가 아니라 시드 장치다.) 그 때문에
  **시드 스키마 버전(`SCHEMA_VERSION`)** 을 도입했다 — 로컬 `.data/nexio.db` 는 파일로
  남아 있어서 컬럼을 추가해도 옛 DB 가 그대로 열려 "no such column" 으로 죽는다.
  버전이 다르면 통째로 다시 만든다(전부 가상 시드라 잃을 게 없다).
- 상세 시트는 조회 화면 것을 **그대로 재사용**한다. 두 벌로 만들면 반드시 어긋난다.
