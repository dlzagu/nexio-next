# ADR-0008: 첨부파일 — 데모 DB 안에 두고, 본문과 한 트랜잭션으로 넣는다

- 날짜: 2026-08-18
- 상태: 채택 (P9.s2 — "반쪽 기능을 구현하거나 걷어낸다" 중 **구현** 쪽으로 확정)

## 맥락

신청 화면에는 '클릭해서 파일 선택'이 있었지만 **파일명 문자열만 state 에 담고 전송하지
않았다.** 서버·스키마·zod 어디에도 첨부가 없었다. 더 나쁜 건 화면 세 곳(신청 폼·댓글창·
처리내역)의 "붙여넣은 이미지는 저장되지 않습니다, **파일로 첨부해 주세요**" 경고가 바로
그 죽은 경로를 가리키고 있었다는 것이다 — 사용자를 없는 기능으로 안내하고 있었다.

선택지는 둘이었다. ① 컨트롤을 걷어내고 "첨부 미지원"을 명시한다 ② 실제로 저장한다.
②를 골랐다. 이 프로젝트가 재현하려는 서비스데스크에서 첨부는 부가 기능이 아니라
**요청의 절반**이고(원본도 2단계 업로드 API 를 따로 뒀다), 무엇보다 세 개의 경고 문구가
가리킬 곳이 필요했다.

## 결정

### 1. 바이트는 데모 DB 의 BLOB 에 넣는다 (`NX_OPTREPORT_FILE`)

외부 스토리지(S3 등)를 붙이면 "클론하면 환경변수 없이 바로 돈다"는 전제가 깨진다
(ADR-0004). 파일시스템도 안 된다 — 배포(Vercel)는 read-only 이고 DB 는 `:memory:` 다.
대신 한도를 좁게 잡았다: **개당 2MB · 합계 5MB · 5개**.

### 2. 형식은 허용 목록이다 (fail-closed)

MIME 과 **확장자가 함께** 맞아야 통과한다 — 이름만 `.png` 로 바꿔서는 못 올린다.
**SVG·HTML 은 일부러 뺐다.** 브라우저가 실행하는 마크업이라 저장형 XSS 통로가 된다.
다운로드는 언제나 `Content-Disposition: attachment` + `nosniff` 로 내려보낸다.

> 판정 기준(`src/lib/attachments.ts`)은 화면과 서버가 **같은 파일**을 본다.
> 화면은 고르는 즉시 거부 사유를 말하고, 서버는 그 말을 믿지 않고 다시 잰다 —
> **디코드한 실제 바이트 길이**로. 클라이언트가 보낸 `size` 는 참고도 하지 않는다.

### 3. 본문과 **한 요청·한 트랜잭션**으로 넣는다

첨부는 base64 로 신청/댓글 본문과 같은 JSON 에 실린다. 별도 업로드 엔드포인트로
나누면 "신청은 저장됐는데 첨부만 실패" 또는 그 반대가 생긴다.

`attachmentStatements()` 는 INSERT 문 배열을 **돌려줄 뿐** 직접 `write()` 하지 않는다.
호출자(`createTicket`·`applyAction`)가 자기 트랜잭션에 얹는다 — 상태 변경과 이력 로그를
한 트랜잭션에 넣는 것과 같은 이유다(ADR-0006 §1). 그래서 첨부가 거부되면
**신청 자체가 저장되지 않는다**(테스트로 고정).

### 4. 읽기는 티켓 가시성 게이트를 다시 지난다

`listAttachments`·`getAttachment` 는 `scopeClause` 를 그대로 쓴다. 파일 id 를 알아도
그 티켓을 볼 수 없으면 받을 수 없고, **접수번호와 id 가 함께** 맞아야 한다.
가시성 밖은 404 — 존재 여부조차 흘리지 않는다.

### 5. 올리는 곳은 둘, 보는 곳은 하나

- 올리기: **신청 폼**과 **댓글창** (같은 `AttachPicker` 컴포넌트)
- 보기: 상세의 **첨부 탭** — 요청·댓글에서 온 파일이 한 목록에 쌓인다
  (첨부가 없는 요청에는 탭 자체를 그리지 않는다. 빈 탭을 열어 "없음"을 확인시키지 않는다)

처리내역(SolutionPanel)에는 업로드를 두지 않았다. 세 번째 업로드 지점을 만드는 대신
경고 문구가 **바로 아래 댓글창의 [파일 첨부]** 를 가리키게 고쳤다.

### 6. 시드에 첨부를 심는다

배포본은 쓰기가 꺼져 있어(`ALLOW_DEV_WRITES`) 업로드를 할 수 없다 → 첨부 화면이
영원히 비어 보인다. 그래서 요청의 약 12% 에 파일을 미리 붙여 둔다.
**열면 실제로 읽히는 텍스트 파일**(로그·CSV·점검표)만 만든다 — 이미지·PDF 는 바이트를
지어낼 수 없어 시드하지 않는다. 내용은 전부 가상이다.

스키마가 늘었으므로 `SCHEMA_VERSION` 2 → 3. 로컬 `.data/nexio.db` 는 자동으로 다시 만들어진다
(⚠️ 개발 서버는 커넥션을 전역 캐시하므로 **재시작**해야 한다).

## 결과 (트레이드오프)

- **얻는 것**: 세 곳의 경고가 가리킬 실제 경로. 신청·댓글 어디서 올려도 한 목록에 모인다.
  새 의존성 0개.
- **포기하는 것**:
  - **대용량**. 2MB 를 넘는 파일은 못 올린다. base64 가 원본의 4/3 이라 요청 본문도 그만큼 커진다.
  - **썸네일·미리보기**. 이미지도 다운로드로만 받는다(`attachment` 강제와 맞바꿨다).
  - **삭제**. 올린 파일을 지우는 경로는 없다 — `write()` 가 INSERT/UPDATE 만 허용하기 때문이다
    (ADR-0006 §1). 지우려면 관문을 넓혀야 해서, 필요해질 때 별도 결정으로 남긴다.
  - **서버리스에서의 수명**: 배포본은 `:memory:` 라 업로드한 파일도 인스턴스 수명까지만 산다.
    시드로 심은 첨부는 콜드스타트마다 다시 생긴다.

## 검토한 대안

- **multipart/form-data 전용 업로드 라우트** — 탈락: 본문과 트랜잭션이 갈라진다(§3).
  zod 스키마 하나를 폼·BFF 가 공유한다는 컨벤션도 깨진다.
- **파일시스템(`.data/uploads/`)** — 탈락: 배포 런타임이 read-only 라 로컬에서만 되는 기능이 된다.
- **첨부 컨트롤 제거 + "미지원" 명시** — 탈락: 그러면 붙여넣기 경고 세 개가 갈 곳을 잃는다.
  "이미지는 파일로 첨부하라"고 안내해 놓고 첨부를 없애면 안내가 거짓말이 된다.
