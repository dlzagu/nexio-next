> 원본 6,611줄 · input 69 · modal 0 · 버튼 25종 · 상태 12 · 권한축 11

## 0. 이 화면의 주된 결정 한 문장 (P1)

> **"내 요청(또는 내가 담당한 요청)이 지금 어디까지 왔고, 다음에 뭘 해야 하는가."**

조회는 이름과 달리 **검색 화면이 아니다.** 실제로는 진행 중인 건을 확인하고 소통하는
**작업 큐**다. 근거 — 미완료 270건(1.1%) 대 완료 23,424건(98.9%). 사용자가 매일 보는 건 앞의 270건이다.

→ **기본 뷰를 "내 진행 중"으로 놓는다.** 전체 2.3만 건 검색은 별도 진입.

### 필터 — 13개 중 상시 4개 (P1)

| 상시 노출                                                          | 접어둠 (`상세 필터`)                                              |
| ------------------------------------------------------------------ | ----------------------------------------------------------------- |
| `keyword`(제목/내용) · `custCode` · `progress` · `fromDate~toDate` | `echoNum` `custPerson` `succPerson` `b1Gubun` `myOnlyYn` `userId` |

> `myOnlyYn` 은 필터가 아니라 **뷰 전환 탭**("내 요청")으로 승격한다 — 가장 자주 쓰는 조건이므로.

### 목록 컬럼 — 7개로 제한

제목 · 고객사 · 담당자 · **단계(Stepper 미니)** · 신청일 · 우선순위 · 댓글배지

> 나머지 95개 필드는 전부 상세로. 현재 목록 화면에 얹혀 있는 상세 편집 컨트롤 56개를 걷어낸다.

### 🆕 컬럼 정렬 (신규 요구, 2026-07-30)

**현재 완전 미구현이다** — 클라이언트에도 서버(`EcoLineSearchVO`)에도 정렬 파라미터가 없다.
Spring 을 수정하지 않으므로 **뷰별로 다르게** 처리한다.

| 뷰                   |     건수 | 정렬 방식                                                         |
| -------------------- | -------: | ----------------------------------------------------------------- |
| 진행 중 / 내 요청    |    270건 | 전체를 한 번에 받아 **클라이언트 정렬** — 전 컬럼, 서버 왕복 없음 |
| 전체 검색 (아카이브) | 23,694건 | 서버 페이징 → **페이지 내 정렬만**. 한계를 UI 에 명시             |

> 매일 쓰는 화면(270건)에서는 정렬·필터가 즉시 동작하고, 서버 API 는 손대지 않는다.
> 아카이브의 정렬 한계는 **숨기지 않고 표기**한다. 상세: `tech-stack.md` §1
> 구현: `@tanstack/react-table` (컬럼 표시/숨김·리사이즈도 함께)

### 🆕 리치 텍스트 (신규 요구)

처리결과 탭의 `cause`·`process`·`improvement`·`answer`·`result` 와 댓글에 **Tiptap** 적용.

- 저장 포맷 HTML → 기존 2.3만 건과 호환
- 기존 데이터 렌더 시 **DOMPurify 새니타이즈 필수** (XSS)
- 상세: `tech-stack.md` §2

### 탭 = 102필드의 수납처 (schema.md 17그룹 매핑)

| 탭           | 담는 그룹                                                   | 필드 수                |
| ------------ | ----------------------------------------------------------- | ---------------------- |

| 1 대기       | 승인 · 반려 · 취소 | —                  |
| 2 신청       | 취소               | **접수**           |
| 3 진행       | 취소요청           | 저장 · 해결안 제시 |

| 9·11·12 종료 | 재신청             | — (전체 잠금)      |

### 🔴 실측으로 드러난 운영 마찰 — "취소를 담당자가 못 한다"

DB 코멘트 이력에서 발견 (2026-07-30). 실제 티켓 한 건(번호·실명 비공개)의 진행 순서:

```
① 현업  "수금취소시 자동 반영됨을 확인하였습니다. 취소처리 요청드립니다."
② 담당  "@담당자A 님, 현업분께서 확인하셨습니다. 해당 건은 취소/완료 처리 부탁드립니다."
③ 담당  "@담당자B 님, 포털에 등록된 신청건의 취소는 신청자 본인이 직접 처리해주셔야
         하는 것으로 확인됩니다."
④ 신청자 "취소하였습니다."
```

**한 건을 취소하는 데 코멘트 4회 왕복.** 원인은 인벤토리에서 본 그대로다:

```js
btnCancel: p === "1" || ("2" && isRequester && isCust); // 신청자 본인만
btnCancelReq: p === "3" && isRequester && isCust; // 역시 신청자만
```

담당자(운영팀)에게는 **취소 버튼이 아예 없다.** 그래서 사람을 찾아 부탁해야 한다.
게다가 `btnCancelReq` 가 만드는 상태 10(취소요청)은 **전 기간 0건** —
즉 대안 경로도 실질적으로 죽어 있다.

### 정책 확정 (2026-07-30, 사용자) — 담당자 직접 취소는 **불가**

> 🔒 **"취소는 신청자 본인만 실행한다"가 회사 정책이다.** 담당자에게 취소 권한을 주는 안은 **폐기**.
> 아래 대응은 이 정책을 지키면서 왕복만 줄인다 — **최종 실행 주체는 언제나 신청자**다.

| 재설계 대응                        | 내용                                                                                                                                | 정책 준수             |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| **담당자 → "취소 권유" 액션 신설** | 담당자가 사유를 적어 보내면 신청자에게 알림이 간다. 실행 버튼은 여전히 신청자 화면에만                                              | ✅ 실행 주체 = 신청자 |
| **신청자 화면에 1클릭 취소 카드**  | 알림 도착 시 상세 상단에 "담당자가 취소를 권유했습니다 — 사유: … [취소하기] [거절]"                                                 | ✅                    |
| 취소 가능 상태를 신청자에게 명시   | 현재는 상태 1·2 에서만 `btnCancel`, 3 에서는 `btnCancelReq`. 신청자도 이 규칙을 모른다 → 상태별로 "지금 취소 가능/불가 + 이유" 표시 | ✅                    |

**효과**: 코멘트 4회 왕복 → 알림 1회 + 클릭 1회.
정책은 그대로 두고 **마찰만** 제거한다.

> 상태 10(취소요청)이 전 기간 0건인 이유는 여전히 미확인이다.
> 위 "취소 권유"를 상태 10 으로 구현할지, 별도 알림으로 둘지는 P5 에서 결정 (open_items).
>
> ⚠️ 이건 화면 미관 문제가 아니라 **매일 발생하는 실제 업무 낭비**다.
> 조회 화면 재설계에서 우선순위가 가장 높은 항목으로 다룬다.
