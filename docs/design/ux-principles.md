# UX 재설계 원칙 — 넥시오 Next.js

> P1 인벤토리 + 실데이터 실측에서 도출. **모든 화면 설계는 이 표를 기준으로 판정한다.**
> 작성 2026-07-30 · 근거: `../inventory/*.md`

## 왜 원칙이 먼저인가

현 화면의 문제는 "촌스럽다"가 아니라 **결정이 안 내려져 있다**는 것이다.
102필드를 어디에 둘지, 25개 버튼 중 뭘 보일지, 12상태를 어떻게 표현할지에 대한 기준이 없어서
"일단 다 보여주기"로 수렴했다. 색과 폰트를 바꿔도 이건 안 고쳐진다.

---

## 원칙 8개

### P1. 한 화면에 한 결정

사용자가 그 화면에서 내려야 하는 판단은 하나다. 나머지는 참조 정보이거나 다른 화면이다.

- **판정 질문**: "이 화면에서 사용자가 눌러야 하는 버튼이 몇 개인가?" 3개를 넘으면 쪼갠다.
- 현재 위반: 조회 화면에 **버튼 25종**이 상태별로 나타난다.

### P2. 안 쓰는 것은 그리지 않는다

"혹시 쓸지 모르니 놔두자"가 지금 화면을 두 배로 만들었다.

| 근거                 | 수치                 |
| -------------------- | -------------------- |
| 시스템이관(상태 7·8) | **전 기간 0건**      |
| 취소요청(상태 10)    | **전 기간 0건**      |
| 테스트(상태 5·6)     | 전 기간 10건 (0.04%) |

- **판정 질문**: "이 UI 가 지난 1년에 몇 번 쓰였나?" 0이면 만들지 않는다.
- **단, 기능을 삭제하는 게 아니다.** 고객사 플래그(`AddInfoVO.testYn`/`systemYn`)가 켜졌을 때만
  렌더한다. 원본이 이미 그 플래그를 갖고 있으므로 손실 없이 접을 수 있다.

### P3. 목록과 상세는 다른 공간이다

현재는 목록에서 행을 고르면 **같은 페이지 아래로 상세가 펼쳐진다**(`selectedRow` 전역).
그래서 스크롤이 무한히 길어지고, 지금 무엇을 보고 있는지가 사라진다.

- 상세는 **사이드 시트(Sheet)** 또는 **별도 라우트**로 분리한다.
- 목록의 스크롤 위치와 필터는 상세를 닫아도 유지된다.

### P4. 액션은 한 곳에 모인다

현재 버튼 시스템이 **두 개** 공존한다 — 상단(고객측 7종) + 하단(엔지니어측 8종).
이건 구현 사정이지 사용자 사정이 아니다.

- 상세 화면에 **단일 액션 바** 하나. 상태 + 권한으로 계산된 것만 표시.
- "내가 지금 할 수 있는 일"이 한눈에 보여야 한다.

### P5. 상태는 보이게 만든다

현재는 진행상태가 코드값/텍스트 한 줄이다. 5단계 워크플로인데 어디까지 왔는지 안 보인다.

- 주 경로 **5단계를 Stepper 로** 시각화: 대기 → 신청 → 진행 → 해결안제시 → 완료
- 종료 상태(완료·취소·반려)는 색과 형태로 즉시 구분.
- 확장 경로(테스트·시스템이관)는 해당 고객사에서만 단계가 추가된다.

### P6. 권한은 단일 함수로, fail-closed 로

현재 권한 축 **11개**가 JSP 전역에 흩어져 버튼마다 조건식이 박혀 있다.

```ts
// 이 형태 하나로 모은다
canDo(action: TicketAction, ticket: Ticket, user: User): boolean
```

- **기본은 차단.** 조건을 만족할 때만 허용한다. 원본 `applyTopButtonsByRow` 가
  "전부 숨김 → 조건 맞으면 show" 구조라 **이미 fail-closed 다. 이 성질을 반드시 유지한다.**
- 서버가 이미 강제하는 것(테넌트 격리·비공개 제한)은 **프론트에서 재구현하지 않는다.**
  두 곳이 어긋나는 순간 구멍이 된다.

### P7. 빈 상태는 이유를 말한다

비공개 문서가 **78.6%**(18,631/23,694)다. 일반 고객사 사용자에게는
목록이 비어 보이는 것이 **정상 동작**인데, 현재 화면은 이를 설명하지 않는다.

- 빈 목록에 항상 이유 + 다음 행동을 제시한다.
  ("권한 범위 내 결과만 표시됩니다" / "필터 초기화" / "검색 범위 넓히기")
- 이것이 "조회가 안 돼요" 문의의 유력한 원인이다. → **UX 개선이 곧 문의 감소다.**

### P8. 밀도는 B2B 기준이다

애플·테슬라·토스의 미감을 **여백으로 번역하지 않는다.**

| 가져올 것                               | 가져오지 않을 것                         |
| --------------------------------------- | ---------------------------------------- |
| 위계의 명확함 (뭐가 중요한지 즉시 보임) | 한 화면에 요소 3개만 두는 소비자 앱 밀도 |
| 부드럽고 절제된 모션                    | 장식적 일러스트·큰 히어로 영역           |
| 색 절제 (강조는 한 곳)                  | 큰 폰트·넓은 행간                        |

- 기준점: **Linear · Stripe Dashboard · Notion**. 하루 8시간 켜놓는 도구다.
- 한글 UI 라 라틴 기준 타이포 스케일을 그대로 쓰면 답답해 보인다 — 행간 보정 필요.

## 판정 체크리스트 (화면 설계마다 통과 확인)

- [ ] 이 화면의 **주된 결정 1개**를 한 문장으로 말할 수 있는가 (P1)
- [ ] 지난 1년 사용 0건인 UI 를 상시 렌더하고 있지 않은가 (P2)
- [ ] 목록과 상세가 같은 스크롤에 섞여 있지 않은가 (P3)
- [ ] 액션 진입점이 화면에 하나인가 (P4)
- [ ] 현재 진행 단계가 텍스트가 아니라 **형태**로 보이는가 (P5)
- [ ] 권한 판정이 `canDo()` 한 곳을 거치는가 · 기본이 차단인가 (P6)
- [ ] 빈 결과일 때 이유와 다음 행동이 있는가 (P7)
- [ ] 데이터 밀도가 소비자 앱이 아니라 업무 도구 수준인가 (P8)

명시해 둔다 — 나중에 "왜 이렇게 했지?" 를 막기 위해.

| 하지 않는 것                 | 왜                                                                |
| ---------------------------- | ----------------------------------------------------------------- |
| 기존 화면을 1:1로 옮기기     | 문제를 그대로 이식하게 된다. 전환의 목적이 사라짐                 |
| 기능 삭제                    | 0건 기능도 **접는** 것이지 없애는 게 아니다. 고객사 플래그로 제어 |
| 프론트에서 권한 재구현       | 서버가 이미 fail-closed 로 강제한다. 이중화 = 구멍                |
| 토스 스타일 여백 그대로 적용 | 데이터 밀도가 근본적으로 다르다 (P8)                              |
| 상태 12개를 모두 1급 UI 로   | 실사용 5단계 + 종료 2 = 7개. 나머지는 확장 경로                   |
