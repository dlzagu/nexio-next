# PRD — 넥시오 벤더포털 Next.js 재구축 (포트폴리오 사이드 프로젝트)

> **확정된 것만 적혀 있고, 미확정은 `⬜ 미확정` 으로 표시했다.**
> 추측으로 채우지 마라 — 사용자와 확정한 뒤 표시를 지우고 내용을 넣는다.
>
> 전제: 2026-08-14 **포트폴리오 전환**(`decisions/ADR-0004`) 이후 기준이다. 그 전의
> "사내 운영 대체 · Spring 백엔드 위 BFF" 전제는 폐기됐고, 원본에서 관찰한 사실은
> §8 에 역사 기록으로만 남긴다.

## 1. 문제

기존 벤더포털의 서비스 조회 화면(`c4web/ST001.jsp`)이 **6,611줄 한 화면**이다.
목록·상세·편집·워크플로 액션이 한 페이지에 세로로 눌려 있고, 상태 12종 × 버튼 25종 ×
권한 축 11개가 JSP 전역에 흩어져 있다. 유지보수 비용과 사용자 인지 부하가 모두 높다.

실측(`inventory/data-profile.md`)이 밝힌 더 큰 문제 — **화면에 있는 워크플로의 일부가
도입 이래 한 번도 실행되지 않았다**(상태 7·8·10 = 전 기간 0건). 쓰지 않는 단계를 위해
필드 8개 · 버튼 3개 · 권한 축 4개 · 상태 분기 2블록이 상주 중이다.

## 2. 목표

- 원본 3화면(대시보드·조회·신청)을 Next.js 로 재설계·재구축하고, 정보 구조를
  **단계/패널/모달로 분해**한다 — "사내에서 이런 것을 만들었다"를 보여 주는 포트폴리오
- **독립 실행** — 자체 SQLite + 가상 시드(`src/lib/dev-seed/`). 클론 직후 계정·VPN·환경변수
  없이 `npm run dev` 로 돈다 (ADR-0004)
- **공개 라이브 데모** — Vercel 배포 + 공유 DB(libSQL)로 라이브에서도 저장이 동작한다
  (ADR-0005 · ADR-0009)
- 디자인 방향: 애플·테슬라·토스 계열의 미니멀·직관·세련됨 (B2B 밀도는 유지)

## 3. 비목표 (Non-goals)

- 원본 시스템(Spring·MSSQL) 연동 · 운영 대체 — ADR-0004 로 폐기
- 실데이터·실명 — 회사 DB 데이터·실고객사명·실계정은 코드·시드·문서 어디에도 넣지 않는다
- 원본 repo(SVN) 로의 커밋, 원본의 내용·경로·사명을 이 저장소로 복사하는 것
- ST003(선급금 정산) · ST004(Cross charge) — 원본에서 통로가 달랐고 이식 대상에서 뺐다
- 원본 내부관리(`admin/*`) 화면 전체 — **고객사 관리 1종만 예외로 이식**(ADR-0010).
  고른 기준과 버린 근거는 ADR-0007
- 다국어 — 한국어 전용. i18n 라이브러리 도입 금지

## 4. 사용자

`Const.java:58~62` 정본 기준 3종. TS 이식 시 이름을 바꿔 쓴다.

| 원본 코드 | 원본 이름 | 우리 이름 | 설명 |
|---|---|---|---|
| `B0001_01` | INTERNAL | `INTERNAL` | 내부 운영팀 |
| `B0001_02` | EXTERNAL | `CUSTOMER` | 고객사 직원 (이름이 오해를 부른다) |
| `B0001_03` | — | `VENDOR` | 외부 업체 |

데모는 이 3종을 **가상 인물 4명**(운영팀 · 고객사 승인권자 · 고객사 일반 · 외부업체)으로
나눠, 상단 바의 역할 전환으로 권한별 차이를 직접 볼 수 있게 한다 (ADR-0004).

## 5. 범위

### 5-1. MVP 3화면 — 완료

구현 순서 = 대시보드 → 조회 → 신청.

| 화면 | 원본 | 규모 | 성격 | 인벤토리 |
|---|---|---|---|---|
| 대시보드 | `views/ndashboard.jsp` | 3,104줄 · GET 14 | 읽기 전용 | `inventory/ndashboard-대시보드.md` |
| 조회 | `c4web/ST001.jsp` | 6,611줄 · 상태 12 · 버튼 25 | **최난도 · 핵심 목표** | `inventory/ST001-조회.md` |
| 신청 | `c4web/ST002.jsp` | 2,599줄 · 입력 20 | 가장 가벼움 | `inventory/ST002-신청.md` |

쓰기 경로(신청 저장·상태 전이 액션·댓글·첨부)까지 포함한다 — 한 트랜잭션·이력 동반
(ADR-0006 · ADR-0008). 구현 순서의 근거는 `progress/nexio-mvp.json` `design_decisions.구현순서`.

### 5-2. MVP 이후 이식·확장 — 완료

| 화면 | 무엇 | 근거 |
|---|---|---|
| 업무 현황 `/board` | 조회와 같은 데이터의 칸반 시점. 카드 이동이 같은 액션 라우트를 쓴다 | ADR-0007 |
| 공지사항 `/notices` | 대시보드 공지 위젯이 막다른 길이던 것을 목록·상세로 | ADR-0007 |
| 알림센터 (상단 종) | 담당자의 '취소 권유' 등이 신청자에게 닿는 통로. 읽음선에서 파생 | ADR-0007 |
| 고객사 관리 `/customers` | 등록·비활성(삭제 아님), 권한 2단 | ADR-0010 |
| 업무 등록 (보드 안) | 전화·메일·내부 업무 대리 등록 + 정기 업무 템플릿 | ADR-0011 |

보조 화면: `/styleguide` — 토큰·컴포넌트를 한눈에 보는 살아 있는 스타일가이드
(디자인 시스템 정본은 `design/` — `tokens.css` · `styleguide.html`).

## 6. 성공 기준

⬜ **미확정** — 사용자와 확정할 것.

포트폴리오 전환으로 **실사용자가 없어져** 원래 후보 중 일부는 잴 수 없게 됐다. 정해야 할 것:

1. **관점** — 원본 대체 관점의 지표를 버리고 포트폴리오 관점("리뷰어가 무엇을 직접
   확인할 수 있어야 하나")으로 바꿀지
2. **실사용자가 있어야 재는 후보를 어떻게 할지** — 폐기할지, 가상 과업 시나리오로 대신 잴지
   - 조회 화면에서 "다음에 뭘 해야 하나"를 파악하는 데 걸리는 시간
   - 기존 화면 대비 문의 감소 (특히 "조회가 안 돼요" — 비공개 다수가 유력 원인)
3. **지금도 잴 수 있는 후보 중 무엇을 '기준'으로 올릴지** — 올린다면 목표치도 함께 정한다
   - 화면당 초기 로드 시간 / 브라우저 요청 수 (대시보드는 원본 19+ → 1 이 설계 목표였다)
   - 신청 완료까지의 클릭·입력 수
   - 이미 자동으로 재고 있는 것: CI(verify·스모크·반응형), Lighthouse(`docs/measurements/summary.md`)

## 7. 제약 (현행)

- 기존 데이터 2.3만 건이 이스케이프된 HTML 로 저장돼 있다(시드도 이 형태를 재현한다)
  → 디코드 후 새니타이즈 필수, 저장 시점에도 새니타이즈
- 회사 정책: 요청 취소의 실행 주체는 **신청자 본인만**
- 권한 게이트는 fail-closed — 규칙에 없는 조합은 전부 거부. 판정은 서버(라우트)가 집행한다
- 쓰기 허용 여부는 저장소가 정한다 — 로컬 파일 DB = 허용 · 서버리스 메모리 = 잠금(202) ·
  공유 DB = 허용 (ADR-0009)
- 서버리스라 스케줄러가 없다 — 정기 업무는 사람이 버튼으로 이번 달 회차를 만든다 (ADR-0011)
- 목록 정렬 — 진행 중·내 요청 뷰는 전량을 받아 클라이언트가 정렬하고, 아카이브는 페이지 안에서만
  정렬하며 그 한계를 화면에 적는다 (아래 §8 의 원본 제약에서 나온 설계가 유지되고 있다)

## 8. 원본 시스템에서 관찰한 것 (역사 기록 — 지금 코드의 제약이 아니다)

- 원본 API 는 정렬 파라미터를 지원하지 않았다 → 뷰를 나눠 클라이언트/서버 정렬을 병행하는 설계가 나왔다
- 원본 인증은 form-login + 세션 쿠키(`PORTALSESSIONID`)였다. BFF 가 그 세션을 릴레이하려던
  설계가 ADR-0001 이고, 지금은 **대체됨**(ADR-0004)

## 9. 열린 항목
