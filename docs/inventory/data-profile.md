## 2. 🔴 핵심 발견 — 화면 복잡도의 절반이 "쓰이지 않는 기능"이다

### 2-1. 시스템이관 워크플로: **전 기간 0건**

`PROGRESS IN ('7','8','10')` = **0건**. 시스템 도입 이래 한 번도 발생하지 않았다.

그런데 조회 화면(ST001)은 이 단계를 위해 아래를 전부 유지하고 있다:

| 유지 중인 자산          | 규모                                                                                                            |
| ----------------------- | --------------------------------------------------------------------------------------------------------------- |
| 필드 (schema.md 그룹 J) | `systemYn` `systemDt` `systemer` `systemComDt` `systemComer` `systemSelfYn` `systemBy` `lineSystemYn` — **8개** |
| 버튼                    | `btnSystemReq` `btnSystemApprove` `btnCompleteCust` — 3개                                                       |
| 상태 분기               | `p==='7'` `p==='8'` 블록 (`applyProgressUI` L5729~5753)                                                         |
| 권한 축                 | `systemSelfYn` `systemAppYn` `systemSuccYn` `canSystem` — **4개**                                               |
| 상단버튼 분기           | `applyTopButtonsByRow` 의 7·8 블록                                                                              |

### 2-2. 테스트 워크플로: 전 기간 **10건 (0.04%)**

`PROGRESS IN ('5','6')` = 10건. 필드 6개(`testYn` `testDt` `tester` `testComDt` `testComer` `lineTestYn`) + 버튼 2개(`btnTestReq` `btnTestComplete`) + 상태분기 2개를 유지 중.

### 2-3. 그래서 실질 워크플로는 **5단계**다

```
실제로 도는 경로 (99.9%)
  1 대기 → 2 신청 → 3 진행 → 4 해결안제시 → 9 완료
                                  ├→ 11 취소
                                  └→ 12 반려

거의 안 도는 경로 (0.04%)        한 번도 안 돈 경로 (0%)
  4 → 5 테스트요청 → 6 테스트완료   7 시스템이관요청 → 8 시스템이관승인
                                    10 취소요청
```

> **P2 결론**: 12상태 × 버튼 25종 × 권한축 11개를 그대로 옮기지 마라.
> 주 경로 5단계를 1급 UI로 만들고, 테스트/시스템이관은 **고객사 설정(`testYn`/`systemYn`)이
> 켜졌을 때만 렌더되는 확장 경로**로 격리한다. 원본이 이미 그 플래그를 갖고 있으므로
> (`EcoLineAddInfoVO`) 기능을 잃지 않으면서 기본 화면을 절반으로 줄일 수 있다.

## 3. 진행 중 건수 = 270건 (1.1%)

전체 23,694건 중 **미완료(9·11·12 제외)는 270건**뿐이다.

| 함의                                              | 설계 반영                                                               |
| ------------------------------------------------- | ----------------------------------------------------------------------- |
| 사용자가 실제로 "일하는" 대상은 수백 건 규모      | 목록 기본 뷰는 **미완료 우선**. 전체 2.3만 건을 기본으로 깔 이유가 없다 |
| 완료건 94.9% 는 검색·참조 용도                    | 완료건은 **검색 진입**으로 분리 (아카이브 성격)                         |
| 대시보드 "내 미처리"(`my-pending`)가 실질 작업 큐 | 대시보드 → 조회 진입 동선의 주축                                        |

## 4. 비공개 문서가 **78.6%**

`PUBLICYN='N'` = **18,631건 / 23,694건**.

`DashController.restrictPrivate()` 기준으로, **고객사 일반 사용자**는
공개분 + 본인 작성 비공개분만 볼 수 있다. 즉 **대부분의 데이터가 대부분의 사용자에게 안 보인다.**

> 🔴 **UX 리스크**: 일반 고객사 사용자에게는 목록이 비어 보이는 상황이 정상이다.
> 지금 화면은 이걸 설명하지 않는다 → "조회가 안 돼요" 문의의 유력한 원인.
> **빈 목록 상태(empty state)에 이유를 명시**해야 한다.
> ("권한 범위 내 결과만 표시됩니다" 같은 안내 + 필터 초기화 동선)

## 7. 조회 근거 (재현용, 전부 read-only)

```sql
-- 상태 코드 정본
SELECT UPPER_CD, CD, CD_NM FROM COMMON_CODE WHERE UPPER_CD='STEPSTAT';

-- 상태 분포
SELECT PROGRESS, COUNT(*) FROM NX_OPTREPORTD GROUP BY PROGRESS;

-- 품질/비중 요약
SELECT COUNT(*) AS 전체,
       SUM(CASE WHEN REQDATE < '2015-01-01' THEN 1 ELSE 0 END) AS 과거이상치,
       SUM(CASE WHEN REQDATE > '2026-12-31' THEN 1 ELSE 0 END) AS 미래이상치,
       SUM(CASE WHEN PROGRESS IN ('7','8','10') THEN 1 ELSE 0 END) AS 이관취소요청,
       SUM(CASE WHEN PROGRESS IN ('5','6') THEN 1 ELSE 0 END) AS 테스트단계,
       SUM(CASE WHEN PUBLICYN='N' THEN 1 ELSE 0 END) AS 비공개
FROM NX_OPTREPORTD;
```
